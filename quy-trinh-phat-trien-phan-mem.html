#Quy trình phát triển phần mềm AI‑Native kết hợp AI Agent và Plugin Superpowers

Phiên bản: 1.0
Ngày: 25/05/2026
Ngôn ngữ: Tiếng Việt
Mục tiêu: Xây dựng một quy trình phát triển phần mềm chuẩn, có thể áp dụng cho đội R&D/Product/QA/DevOps, kết hợp Spec‑Driven Development, AI Agent, Plugin Superpowers, GitHub/Lark/CI/CD/Test Automation để tăng tốc phát triển nhưng vẫn kiểm soát chất lượng, rủi ro và ownership.

#0. Cách dùng tài liệu này

Tài liệu này dùng để:

  1. Thiết kế quy trình phát triển phần mềm chuẩn cho công ty.
  2. Huấn luyện PM/PO/BA/UX/Dev/QA/DevOps/SRE về cách làm việc với AI Agent.
  3. Tạo template cho từng giai đoạn: từ ý tưởng → đặc tả → thiết kế → kiến trúc → plan → task → code → test → release → vận hành.
  4. Thiết lập quality gate để tránh các lỗi thường gặp: thiếu spec, đổi yêu cầu liên tục, bàn giao mơ hồ, QA phát hiện muộn, claim sản xuất thiếu tài liệu, ownership chồng chéo.
  5. Biến AI Agent thành “nhân sự số” có vai trò, nhiệm vụ, quyền hạn, KPI và cơ chế giải trình rõ ràng.

Các sơ đồ trong tài liệu dùng Mermaid diagram. Có thể xem trực tiếp trên GitHub, GitLab, nhiều Markdown viewer hiện đại, hoặc VSCode có Mermaid extension.

#1. Tư duy cốt lõi

#1.1. Nguyên lý số 1: Spec là “source of truth”, code là kết quả

Trong mô hình truyền thống, nhiều team bắt đầu bằng code, sau đó mới viết lại tài liệu. Cách này tạo ra 4 lỗi lớn:

Lỗi Hậu quả
Spec mơ hồ Dev hiểu khác, QA test khác, PM kỳ vọng khác
Code đi trước yêu cầu Dễ build sai thứ khách hàng cần
Test viết muộn Lỗi phát hiện cuối phase, chi phí sửa cao
Tài liệu sau release mới viết Bàn giao vận hành/sản xuất/support thiếu chuẩn

Trong mô hình AI‑Native, phải đảo lại:

flowchart LR A["Ý tưởng / Vấn đề"] --> B["PRD: What & Why"] B --> C["SRS: Functional / Non-functional Requirements"] C --> D["UX Flow + Prototype"] D --> E["Architecture + ADR"] E --> F["Plan + WBS + Risk"] F --> G["Task nhỏ có test"] G --> H["AI Agent triển khai code"] H --> I["CI/CD + Review + QA"] I --> J["Release + Monitor"]

Công thức vận hành:

Không có spec rõ → không code.
Không có acceptance criteria → không nhận task.
Không có test → không merge.
Không có monitoring/rollback → không release.
Không có postmortem/learning → không đóng dự án.

#1.2. Nguyên lý số 2: AI Agent không thay con người quyết định, AI Agent tăng tốc vòng lặp

AI Agent mạnh nhất khi được giao:

  • Đọc tài liệu, repo, log, issue.
  • Tóm tắt và chuẩn hóa yêu cầu.
  • Sinh test case, task breakdown, code scaffold.
  • Thực hiện task nhỏ, có tiêu chuẩn kiểm chứng.
  • Tự chạy test, tự sửa, tự review trước khi gửi người.
  • Phát hiện thiếu thông tin và yêu cầu làm rõ.
  • Duy trì traceability giữa requirement → task → PR → test → release.

AI Agent yếu nếu bị giao:

  • Một mục tiêu quá rộng nhưng thiếu context.
  • Một yêu cầu chưa có tiêu chuẩn đúng/sai.
  • Một task không có đầu vào/đầu ra.
  • Một hệ thống không có test, log, data, rule.
  • Một quy trình không có quyền hạn, gate, trách nhiệm.

Vai trò mới của kỹ sư giỏi:

flowchart TB Old["Kỹ sư truyền thống\nTự viết phần lớn code"] --> New["Kỹ sư AI‑Native\nThiết kế môi trường, spec, test, gate, feedback loop"] New --> S1["Đặc tả ý định rõ"] New --> S2["Tạo context cho agent"] New --> S3["Thiết kế test/eval"] New --> S4["Review kiến trúc & rủi ro"] New --> S5["Tối ưu loop tự sửa"]

#1.3. Nguyên lý số 3: Superpowers là lớp “kỷ luật kỹ thuật” cho coding agent

Trong tài liệu này, Plugin Superpowers được hiểu là lớp kỹ năng/phương pháp cho AI coding agent. Nó ép agent không nhảy ngay vào code mà phải đi qua các bước như:

  • Brainstorming.
  • Làm rõ mục tiêu.
  • Viết design/spec.
  • Tạo branch/worktree riêng.
  • Viết implementation plan.
  • Chia task nhỏ.
  • TDD: Red → Green → Refactor.
  • Request/receive code review.
  • Debug có hệ thống.
  • Verify before completion.
  • Kết thúc development branch đúng chuẩn.

Cách hiểu thực dụng:

flowchart LR Prompt["Người giao việc"] --> Agent["AI Coding Agent"] Agent --> SP["Superpowers Skills"] SP --> B["Brainstorming"] SP --> P["Writing Plans"] SP --> T["TDD"] SP --> R["Code Review"] SP --> D["Systematic Debugging"] SP --> F["Finish Branch"] B --> Repo["Repo + PR + CI/CD"] P --> Repo T --> Repo R --> Repo D --> Repo F --> Repo

Superpowers không thay thế quy trình công ty. Nó là engine kỷ luật ở tầng thực thi coding. Quy trình công ty vẫn cần PRD, SRS, kiến trúc, QA, release, vận hành, security, governance.

#0.4. Engineering Constitution mẫu

# Engineering Constitution

## 1. Product First
- Mọi thay đổi code phải liên kết với một requirement hoặc bug rõ ràng.
- Không implement feature chỉ vì “có thể làm”.

## 2. Spec First
- Feature mới phải có PRD/SRS/Acceptance Criteria trước khi code.
- Spec là source of truth; code phải phục vụ spec.

## 3. Test First
- Logic quan trọng phải có unit/integration test trước hoặc cùng lúc code.
- Critical flow phải có E2E/regression test.

## 4. AI Agent Discipline

  • Không có secret/security issue.

#6.4. Definition of Done cho release

  • Deploy thành công.
  • Smoke test pass.
  • Monitoring ổn.
  • Không có incident nghiêm trọng sau release window.
  • Release notes published.
  • Known issues documented.
  • Support/on-call informed.
  • Feedback channel mở.

#25. Kết luận

Quy trình phát triển phần mềm tốt nhất trong thời đại AI không phải là “để AI code càng nhanh càng tốt”. Quy trình tốt nhất là:

Spec rõ → task nhỏ → AI Agent thực thi có kỷ luật → test/eval tự động → review bằng chứng → release an toàn → học lại vào hệ thống.

AI Agent và Plugin Superpowers giúp tăng tốc rất mạnh, nhưng giá trị thật đến từ việc công ty xây được một Operating System phát triển phần mềm với:

  • Source of truth rõ.
  • Artifact chuẩn.
  • Quality gate nghiêm.
  • Traceability đầy đủ.
  • Test/eval tự động.
  • Human review đúng điểm.
  • Agent có quyền hạn và trách nhiệm.
  • Knowledge base liên tục tốt hơn.
